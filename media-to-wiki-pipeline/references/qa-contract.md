# QA placement and reuse

Extend the existing runner and completion ledger. Separate QA responsibilities
and tools without introducing a competing definition of completion.

## Four boundaries

| Boundary | Question | Scope |
|---|---|---|
| Preparation, before model submission | Is the evidence packet usable and correctly bound? | Each affected item |
| Item acceptance, after drafting | Is the proposed content supported and editorially useful? | Each changed artifact |
| Batch integration, before activation | Do accepted items assemble and render correctly together? | One coherent candidate |
| Live delivery, after activation and cache invalidation | Is the accepted version visible at the canonical destination? | Required changed pages/viewports |

Preparation checks required fields, source/body shape, stable identity, canonical
links, contextual aliases and authoritative memberships. Catch cheap defects
before paid work or builds. Identity uncertainty receives a bounded research
disposition rather than a fabricated match.

Item acceptance distinguishes factual support, editorial usefulness and research
coverage. Read proposed prose against its page contract; optional approved
examples illustrate selection and depth, not a mandatory length or outline.
Stream independently ready items. A held replacement does not erase existing
accepted content or block unrelated ready items.

Batch integration checks affected joins, preservation of unrelated content,
routes, navigation and visible presentation. Form one complete candidate before
expensive validation. Follow the project's release gates; reuse checks only when
their relevant inputs are provably unchanged. A shared renderer change can
invalidate multiple page checks; unchanged renderers can support content-only
publication when the destination already supports it.

Live checks bind observed text, identity/bylines, membership, images, layout and
runtime behavior to the published version. Combine desktop/mobile checks into
one pass per changed page/version at the required coverage. Inspect screenshots
where visual acceptance is required. Local QA or pointer readback alone does not
prove live rendering. Readonly cache rechecks do not justify redelivery.

## Where standards live

- Canonical page contracts and writing/identity skills own acceptance criteria.
- Destination policy selects approved examples, participant eligibility, length
  guidance, optional/required media and verification coverage.
- The existing runner enforces required inputs and stage dependencies.
- Batch configuration selects items and budgets; it does not replace prompts or
  weaken acceptance criteria.
- The existing ledger records exact inputs, accepted content, published version,
  actual checks, holds and evidence references.

Keep full receipts behind the ledger. Record factual, editorial, integration and
live outcomes distinctly; do not collapse them into one unexplained `passed`.
When a contract changes, explicitly select outputs for re-evaluation rather than
invalidating the whole accepted corpus automatically.

## Bounded portrait search

Check retained accepted assets and exact organizer records first, then personal
or employer sites and identity-bound public profiles. Use an explicit search
budget proportionate to the task. Four source families or five minutes per
initial search is a possible starting budget, not a universal requirement;
attempt count and a recorded stopping reason make best effort observable.

Record `found`, `not found after bounded search`, `identity uncertain`, or a
specific source/access failure. Retain source URL, identity binding and actual
attempts. Do not report a network failure as proof that no portrait exists.
Respect the task's image-use constraints; discovery does not grant redistribution
rights. Preserve accepted portraits unless a concrete defect warrants change.

For selected images, verify both source identity and destination display:
nonzero natural dimensions, visible rendering, usable crop and no broken image.
A retained URL without a displayed image is an integration defect. Optional
missing portraits need not block good prose; required media remain explicit
outstanding work. Do not generate a likeness to fill a missing real portrait.

## Invalidation and check reuse

| Changed input | Reconsider |
|---|---|
| Biography/company prose | Changed claims and editorial selection; affected page rendering |
| Portrait | Identity/source binding, image loading and affected layouts; no biography rewrite |
| Membership/credit/alias | Affected joins, bylines, routes and directories; prose only where claims change |
| Transcript meaning | Dependent reader/enrichment claims; biographies only where supported claims change |
| Timing or punctuation only | Affected locators/display; no unrelated editorial review |
| Renderer or release mechanism | Affected behavior tests and representative layouts under project gates |

Reuse a receipt only when its relevant source/content, contract, renderer and
environment inputs remain valid. A new public version can reuse unchanged-body
editorial evidence; it still needs required delivery checks for changed pages.
After a repair, rerun the failed or invalidated scope and affected joins, not all
successful model stages, screenshots, builds or immutable-object reads.
Preserve ambiguous attempts and reconcile actual delivery before retrying.

## Completion and throughput

An item can be editorially accepted while its release is pending. A batch can be
integration-ready while live checks are incomplete. Report those distinctions
using the existing ledger; held/unreviewed/unpublished items are not complete.

Measure accepted changes delivered live per elapsed hour. Attribute elapsed time
to useful work, queue waits, retries and duplicated work without double-counting
overlapping stages. Record available usage/costs honestly. Use the measured
critical path to tune concurrency; occupied slots alone are not throughput.

# Bad/good editorial pairs

Use these examples when deciding which shot to use, how to frame it, and when
it should change. Keep the set small. Replace a weaker pair when a later review
illustrates the same decision more clearly.

Evidence: `jay-parikh-overlay-choices-r1.json`, round `jay-universe-r1`.
The comments below are verbatim user feedback. Weak treatments illustrate the
reported issues; better treatments are proposals, not verified edit results.
No before/after media is attached yet. When a pair has been edited and reviewed,
link its versioned before/after excerpts and record what was actually checked.
Use the same dialogue and matching surrounding context for timing comparisons;
frame pairs alone can demonstrate framing, not a successful hold or transition.

## 1. Establish the interface, then show the action

- **Viewer's question:** What does this feature actually do?
- **Weak:** A relevant product screenshot remains throughout an explanation of
  behavior it cannot show.
- **Better:** Establish the interface briefly, then cut to the official keynote
  demo at the spoken beat describing the action visible in that footage.
- **Why:** The visual advances from recognition to evidence of the behavior.
- **When:** Use motion when the action matters. A still can remain useful while
  the speaker explains a static detail; do not cut merely to satisfy a timer.
- **Evidence:** Cue `09` (Keep): "first few frames is good but stays too long, at a good time cut over to the live keynote demo shoiwng that"

## 2. Keep the context around a passage

- **Viewer's question:** What am I reading, and why is this passage relevant?
- **Weak:** A tightly cropped sentence loses its source context and stays on
  screen after the point has landed.
- **Better:** Retain the useful title or nearby context and a readable source
  label. Focus attention on the passage, allow reading time, then return to the
  conversation or advance to the next relevant visual.
- **Why:** The viewer can identify the source and understand the selected detail.
- **When:** Establish a wider view before focusing if orientation needs it.
  Remove empty margins; keep context that changes interpretation. "Flash it"
  means a timely, bounded appearance, not text too brief to read.
- **Evidence:** Cue `03` (Keep): "this is kept up too long and cropped too close. just flash it when relevant,  and include surroudnign context or url"; cue `12` (Keep): "dont crop so close"

## 3. Bring in the graph when the explanation turns to scaling

- **Viewer's question:** How does this change as it grows?
- **Weak:** The previous slide remains while the speaker starts discussing
  scaling; the graph arrives after the relationship has already been explained.
- **Better:** Transition to the scaling graph at that spoken turn, then emphasize
  the relevant trend while retaining its axes, legend and comparison.
- **Why:** The viewer can connect the spoken relationship to the visual evidence.
- **When:** Use the original presentation graph or a faithful sourced treatment.
  Hold it longer if the speaker continues explaining its details; animation is
  useful only when it clarifies the relationship.
- **Evidence:** Cue `11` (Keep): "transition to scaling graph as he starts talking about it"

## 4. Show the person's actual work

- **Viewer's question:** What did this person build, and how does it work?
- **Weak:** A generic skills explainer or unrelated repository substitutes for
  the specific work being discussed.
- **Better:** Show the named person's actual skill files or repository details,
  then the relevant segment of their AI Engineer presentation when it explains
  the example. Scroll purposefully to the referenced material.
- **Why:** The reference becomes concrete and the author supplies useful context.
- **When:** Verify the person, repository and talk match the reference. A useful
  code excerpt can work alone; presenter footage earns its place by adding
  explanation or showing the action.
- **Evidence:** Cue `04` (Alternative): "scroll thru jay's own github?"; cue `05` (Alternative): "show his skills and matt speaking at AIE on his skills"

## 5. Choose the action within the right source

- **Viewer's question:** How was the badge developed or used?
- **Weak:** Show a game's title screen because it belongs to the referenced
  project, even though it demonstrates none of the badge development.
- **Better:** Find the official GitHub video showing the badge being developed
  or used, and choose the specific shot that demonstrates the narrated action.
- **Why:** Source identity and shot relevance are separate editorial checks.
- **When:** A title screen can establish the work's identity, but the development
  explanation needs an action or artifact that actually shows it. If unavailable,
  report the gap and use the interview rather than inventing product behavior.
- **Evidence:** Cue `13` (Keep): "bad game title screen choice. search github youtube channelf or video of the badge developmetn"

Cue `13` also illustrates feedback precedence: its written replacement request
controls the edit despite the Keep label. Blank keeps and tentative acceptance
such as cue `10`'s "not sure but i guess ok" are weak evidence of general taste.
